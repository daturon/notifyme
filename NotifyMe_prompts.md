# NotifyMe — промпты для вайбкодинга

Как пользоваться: выполняйте промпты по порядку, каждый — отдельным сообщением агенту (Claude Code, Cursor и т.п.) в том же проекте/репозитории. После каждого шага — проверяйте, что всё собирается и работает, прежде чем идти дальше. Промпты 1–4 — обязательный костяк, 5–6 — два кейса (можно менять порядком или делать один), 7–10 — доводка.

В начале каждой новой сессии агента (если контекст обнулился) приложите файл `NotifyMe_TZ.md` целиком — промпты на него ссылаются.

## Промпт 6. Кейс 2: курс обмена RUB → BYN (по тренду за 14 дней)

```
Прикладываю ТЗ (NotifyMe_TZ.md), раздел 4.2 (обновлённая версия — логика
скользящего окна) и раздел 9 п.1-2, и раздел 5 (таблица rate_history).

Я решил источник данных так: [ВПИШИ СЮДА СВОЙ ВЫБОР — например: "буду сам
поддерживать список из 3-5 URL обменных пунктов, парсер работает по этому
списку" ИЛИ "используем агрегатор X, вот пример страницы с курсами: <ссылка>"].

Реализуй тип триггера 'exchange_rate' по следующей логике (НЕ простое сравнение
с фиксированным порогом — сравнение с историей за 14 дней):

1. Миграция: добавь таблицу rate_history по схеме из раздела 5 ТЗ.

2. lib/triggers/exchangeRate.ts — провайдер, который:
   a. получает текущие курсы RUB->BYN по источникам из конфига события
      (список источников — как я указал выше), параллельно (Promise.all),
      с таймаутом на каждый запрос (учти лимит 10 сек на serverless-функцию
      Vercel Hobby в сумме на весь check());
   b. находит максимальный (лучший для сдачи RUB) курс среди источников на
      сегодня;
   c. сохраняет сегодняшний лучший курс в rate_history (upsert по
      event_id+source_name+recorded_at, чтобы повторный запуск в тот же день
      не плодил дубли);
   d. берёт из rate_history записи за последние 14 дней (включая сегодня) по
      этому event_id;
   e. если истории меньше 14 дней (только запустили) — НЕ триггерит
      уведомление, просто накапливает данные, но пишет в run_log, что
      "недостаточно истории для оценки, накоплено X из 14 дней";
   f. считает среднее и максимум за окно;
   g. triggered = true, если: сегодняшний курс равен максимуму за окно
      И сегодняшний курс >= среднее за окно * (1 + threshold), где threshold
      берётся из config (по умолчанию 0.01 = 1%);
   h. дополнительно вычисляет тренд за последние 2 дня (рост/падение/без
      изменений) — только для текста письма, не влияет на triggered.

3. Обработай случай, когда источник недоступен или формат страницы
   изменился — не должен падать весь cron, только это событие, с логом
   ошибки в run_log; если хотя бы один источник ответил успешно — используй
   то, что получилось.

4. UI-форма конфигурации для этого типа (вместо сырого JSON): размер окна в
   днях (по умолчанию 14), порог превышения над средним в % (по умолчанию 1%),
   список отслеживаемых точек (чекбоксы/мультиселект из доступных источников).
   На странице события добавь мини-график последних 14-30 значений из
   rate_history (просто линия, любая лёгкая библиотека или SVG вручную — не
   усложняй).

5. Юнит-тесты: на парсинг источников (с замоканным HTML-ответом), на расчёт
   среднего/максимума за окно, и отдельно — на граничные случаи (истории
   меньше 14 дней; курс равен максимуму, но не дотягивает до порога над
   средним; несколько дней подряд равный максимум).
```

## Промпт 7. Notification Engine и интеграция с Resend

```
Прикладываю ТЗ (NotifyMe_TZ.md), раздел 4.4.

Реализуй lib/notifications/engine.ts:

1. Функция notifyIfNeeded(event, checkResult):
   - проверяет, не отправлялось ли уже уведомление по этому event сегодня
     (по notification_log)
   - если triggered=true и сегодня ещё не отправляли — формирует письмо и
     отправляет через Resend
   - логирует результат (успех/ошибка) в notification_log
   - при ошибке отправки делает один retry, затем логирует failed и НЕ бросает
     исключение наружу (чтобы не сломать обработку остальных событий)

2. Шаблоны писем (простой HTML, можно через react-email, если это не усложнит
   сборку) отдельно для каждого типа события — используй payload из
   checkResult провайдера. Для weather_task, если сработало несколько задач
   одновременно — объедини их в одно письмо (см. п.4.3 ТЗ).

3. Тестовый режим: возможность отправить тестовое письмо на свой адрес прямо
   из UI (кнопка "отправить тестовое письмо" на странице события), не завязанная
   на реальное срабатывание триггера — просто чтобы проверить, что Resend
   настроен верно.

Используй переменную окружения RESEND_API_KEY (уже есть в .env.example).
```
