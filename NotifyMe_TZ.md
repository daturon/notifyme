## 1. Общее описание

NotifyMe — персональное приложение для мониторинга произвольных событий и отправки email-уведомлений при наступлении заданных условий. Приложение однопользовательское (single-user), деплоится на Vercel (бесплатный Hobby-план), фронтенд на React.

Ключевая идея: не «одно приложение под одну задачу», а **платформа с расширяемыми типами триггеров** — на старте два конкретных кейса, но архитектура должна позволять добавлять новые типы без переписывания ядра.

### 1.1 Кейсы на старте (MVP)

1. **Курс обмена RUB → BYN в Жлобине.** Отслеживание курсов в пунктах обмена/банках города, уведомление, когда появляется оптимальный (наиболее выгодный) вариант сдать рубли.
2. **Погодные рекомендации по хозяйственным работам.** Пользователь ведёт список периodических работ по дому (покос травы, фасадные работы и т.д.), приложение сопоставляет прогноз погоды с условиями для каждой работы и раз в день присылает рекомендацию, что стоит сделать в ближайшие дни.

### 1.2 Ограничение частоты

Не более **одного email-уведомления в сутки на одно событие** (event), независимо от того, сколько раз внутри суток сработал бы триггер.

## 3. Архитектура и поток данных

```
┌─────────────┐      ┌──────────────────┐      ┌───────────────┐
│   React UI  │◄────►│  Next.js API      │◄────►│  Postgres (DB)│
│ (настройка  │      │  (CRUD событий,   │      │  events,      │
│  событий)   │      │   ручной запуск)  │      │  jobs, logs   │
└─────────────┘      └──────────────────┘      └───────────────┘
                              ▲
                              │ вызывает раз в сутки
                      ┌───────┴────────┐
                      │  Vercel Cron   │
                      │  /api/cron/run │
                      └───────┬────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
     ┌─────────────┐  ┌──────────────┐  ┌───────────────┐
     │ RUB/BYN      │  │ Weather      │  │ Будущие типы   │
     │ провайдер    │  │ провайдер    │  │ триггеров      │
     │ (парсинг/API)│  │ (Open-Meteo) │  │ (plugin-модель)│
     └──────┬───────┘  └──────┬───────┘  └───────┬────────┘
            └──────────────────┼───────────────────┘
                                ▼
                        ┌──────────────┐
                        │ Notification  │
                        │ Engine        │
                        │ (throttling,  │
                        │ дедупликация) │
                        └──────┬───────┘
                                ▼
                        ┌──────────────┐
                        │ Resend (Email)│
                        └──────────────┘
```

**Принцип работы cron-обработчика (`/api/cron/run`):**

1. Vercel Cron дергает эндпоинт раз в сутки (например `0 5 * * *` — в районе 5:00–5:59 UTC).
2. Обработчик выбирает из БД все активные события (`events`, `is_active = true`).
3. Для каждого события вызывает соответствующий **провайдер-триггер** (по `event.type`), который возвращает: сработало условие или нет, и если да — текст/данные для уведомления.
4. Если условие сработало и по этому событию сегодня ещё не отправлялось письмо — Notification Engine отправляет email и пишет запись в `notification_log`.
5. Все запуски логируются в `run_log` для отладки (в т.ч. случаи, когда условие не сработало).

## 4. Функциональные требования

### 4.1 Управление событиями (общее для всех типов)

Пользователь в UI может:

- создать событие: указать **название**, **тип триггера**, **параметры триггера** (JSON-конфиг, специфичный для типа), включить/выключить;
- редактировать и удалять события;
- посмотреть историю срабатываний и отправленных уведомлений по событию;
- вручную запустить проверку события («проверить сейчас») — без отправки письма, просто посмотреть текущий результат (полезно для отладки, не расходует лимит уведомлений);
- задать email(-ы) получателя (по умолчанию — один, свой).

### 4.2 Триггер типа «Курс обмена RUB → BYN, Жлобин»

**Параметры конфигурации:**

- город/точки мониторинга (на старте фиксировано — Жлобин, но поле должно быть готово к расширению на другие города);
- минимальная сумма сделки (опционально, если курсы зависят от суммы);
- условие срабатывания: например «курс выше N BYN за 1000 RUB» или «текущий курс входит в топ-1 среди всех отслеживаемых точек и лучше среднего за последние 7 дней на X%» (нужно решить, см. раздел 9).

**Логика:**

1. Провайдер получает актуальные курсы по всем доступным пунктам обмена/банкам в Жлобине (набор источников — открытый вопрос, см. раздел 9).
2. Определяет оптимальный (максимальный) курс сдачи RUB.
3. Сравнивает с порогом/условием из конфигурации.
4. Если условие выполнено — формирует текст письма: «Лучший курс сегодня: [банк/пункт], [курс], адрес/контакты».

**Уведомление содержит:** название пункта обмена, курс, дата/время получения данных, ссылка на источник (если применимо).

### 4.3 Триггер типа «Погодные рекомендации по домашним работам»

**Модель данных «Работа» (Task), которую заводит пользователь:**

- название (например «Покос травы», «Фасадные работы»);
- периодичность / желаемый интервал между выполнениями (например «раз в 2 недели», «раз в сезон»);
- погодные условия-предпосылки (например: «нет дождя последние N дней», «температура выше X°C», «нет дождя в ближайшие M дней подряд» — для фасадных работ важно окно сухой погоды);
- дата последнего выполнения (пользователь отмечает вручную, когда выполнил работу — важно для расчёта, не «просрочена» ли задача и не будет ли рекомендация повторяться слишком часто).

**Логика:**

1. Раз в сутки для каждой активной задачи система смотрит: (а) прошло ли достаточно времени с последнего выполнения, с учётом заданной периодичности; (б) подходят ли погодные условия сейчас / в ближайшие дни (используя прогноз Open-Meteo на 5–7 дней вперёд).
2. Если задача «созрела» по времени **и** погода благоприятна — генерируется рекомендация.
3. Если задач, «созревших» одновременно, несколько — они объединяются в одно письмо (одно уведомление в сутки на событие/группу, не спам по одному письму на задачу).
4. Пользователь после выполнения работы отмечает её как выполненную в UI (обновляется дата последнего выполнения) — это выключает повторные рекомендации до следующего цикла.

**Уведомление содержит:** список рекомендованных на ближайшие дни работ с кратким обоснованием («благоприятное окно 3 дня без дождя, 22–26°C»).

### 4.4 Notification Engine (общий для всех типов)

- Дедупликация: одно письмо в сутки на событие, даже если триггер проверяется чаще (на MVP это не требуется, т.к. cron сам ходит раз в сутки, но правило должно быть заложено в схему на будущее — если позже понадобится проверять чаще, а слать реже).
- Логирование всех отправленных писем (`notification_log`: event_id, timestamp, содержимое, статус доставки).
- Обработка ошибок отправки (retry один раз, лог ошибки, не блокирует проверку остальных событий).

## 5. Модель данных (черновая схема)

```sql
-- события
events (
  id            uuid primary key,
  name          text not null,
  type          text not null,        -- 'exchange_rate' | 'weather_task' | ...
  config        jsonb not null,       -- специфичные для типа параметры
  is_active     boolean default true,
  recipient_email text not null,
  created_at    timestamptz default now(),
  updated_at    timestamptz default now()
)

-- задачи по дому (специфично для типа weather_task, могут быть вложены в config
-- события ИЛИ вынесены в отдельную таблицу, если нужен независимый CRUD по задачам)
household_tasks (
  id              uuid primary key,
  event_id        uuid references events(id),
  title           text not null,
  interval_days   int not null,
  weather_rules   jsonb not null,     -- условия погоды
  last_done_at    date,
  created_at      timestamptz default now()
)

-- лог каждого запуска cron-проверки (для отладки и истории)
run_log (
  id            uuid primary key,
  event_id      uuid references events(id),
  ran_at        timestamptz default now(),
  triggered     boolean,
  raw_result    jsonb          -- сырые данные провайдера (курсы, прогноз и т.д.)
)

-- лог отправленных уведомлений
notification_log (
  id            uuid primary key,
  event_id      uuid references events(id),
  sent_at       timestamptz default now(),
  subject       text,
  body          text,
  status        text            -- 'sent' | 'failed'
)
```

## 7. Нефункциональные требования

- **Стоимость:** $0/мес — только бесплатные тарифы (Vercel Hobby, Resend Free, Supabase Free, Open-Meteo).
- **Ограничения Vercel Hobby, которые нужно учитывать:**
  - функции выполняются не дольше 10 секунд по умолчанию — провайдеры (парсинг курсов, запрос погоды) должны укладываться в этот лимит или использовать `maxDuration` (доступно и на Hobby, но с потолком);
  - cron срабатывает **в пределах часа**, а не в точное время — не полагаться на точность до минуты;
  - Hobby-план формально предназначен для некоммерческого личного использования — это соответствует характеру проекта;
  - 100 cron job'ов на проект — с запасом для будущих типов триггеров, но чтобы не плодить по одному job на событие, лучше **один общий cron**, который сам итерирует по всем активным событиям в БД (иначе легко упереться в лимит function invocations на Hobby при росте числа событий).
- **Безопасность:** cron-эндпоинт закрыт секретным токеном; доступ к UI закрыт простой авторизацией (см. раздел 9); email-адреса и данные не публикуются.
- **Расширяемость:** каждый новый тип триггера — это модуль-провайдер с единым интерфейсом `check(config) -> { triggered: boolean, payload }`, регистрируемый в реестре типов. Добавление нового кейса не должно требовать изменений в Notification Engine или UI-каркасе (только новую форму конфигурации на фронте и новый провайдер на бэке).

## 8. UI (React) — минимальный состав экранов

1. **Список событий** — карточки с названием, типом, статусом (активно/выключено), датой последней проверки и последнего уведомления.
2. **Создание/редактирование события** — выбор типа из реестра, динамическая форма конфигурации в зависимости от типа.
3. **Экран настройки задач по дому** (для типа `weather_task`) — список задач, добавление/редактирование, кнопка «отметить выполненным».
4. **История/лог** по событию — таблица запусков и отправленных писем.

## 9. Открытые вопросы (требуют решения перед началом разработки)

1. **Источник данных по курсам обмена в Жлобине.** Официального API нет. Варианты: (а) парсинг агрегатора вроде myfin.by, если там есть данные по конкретному городу; (б) парсинг сайтов конкретных банков/обменников вручную заданным списком; (в) отказ от автоматизации и ручной ввод курсов пользователем (не соответствует цели «мониторинг», но проще всего). **Нужно решить до старта разработки** — от этого зависит трудоёмкость и надёжность первого кейса.
2. **Точная формула «оптимального курса».** Простое сравнение с порогом, или сравнение с историческим средним/трендом?
3. **Погодные правила по умолчанию** для типовых работ (покос травы, фасадные работы) — нужно один раз сформулировать конкретные критерии («N дней подряд без дождя», диапазон температур и т.д.), чтобы заложить их как шаблоны в UI.
4. **Авторизация.** Т.к. приложение публично доступно на *.vercel.app, нужна хотя бы простая защита (логин/пароль через переменную окружения, или Vercel Deployment Protection — но она доступна не на всех тарифах для прод-доменов). Нужно решить, что использовать.
5. **Часовой пояс.** Vercel Cron работает в UTC — нужно явно указать, в какое локальное время должно приходить письмо, и рассчитать смещение (с учётом перехода на летнее/зимнее время, если это учитывается в регионе пользователя).
